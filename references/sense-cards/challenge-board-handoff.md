# challenge-board-handoff

## 何時用

- 目標是**刻意漏洞／訓練用 Web 應用**（自建 lab、OWASP 類 scoreboard、挑戰盤），且本場已能列到挑戰／任務／進度盤（API 或 UI 列表皆可）。
- 公開 observe／指紋已齊，卻仍只交「再觀察」選項時——**強制改交可稽核下一階**。

## 要驗證什麼

1. HAVE 裡是否已有：**挑戰／任務列表的本場觀測**（名稱可記、狀態可記；禁止把外部 writeup 清單當本場證據）。
2. 是否已有（或明確缺）合法工作階段；缺則先走 `session-break-rebuild`／身分面，不跳挑戰利用。
3. 下一提案是否寫成**窄、可稽核、需指揮批**的一階（見下方交班句式），而不是整條殺傷鏈。

## 證據門（達標相關）

對齊封條常見最低門（方法層，非解法）：

| 目標類 | 合格本場證據 |
|---|---|
| 管理面可達 | 管理路由／面板實際回應可複核（狀態＋身分脈絡），非只猜路徑名 |
| 單一挑戰完成 | 挑戰狀態變更或同等成功訊號＋對應請求／回應入戰情 |

Strong（多挑戰）非預設必須；本卡先逼出**最低可稽核進展**的授權請求。

## 交班句式（HANDOFF 建議選項必須長這樣）

擇一具名（其餘作備選），標 `[CONFIRM-REQUIRED]`：

- **挑戰向・單階**：「授權對挑戰盤上已列之〈名稱或 id〉做**單一**可稽核嘗試（只記成敗證據；禁止噴射／批量）」
- **管理面・只讀探達**：「授權只讀探測管理面是否可達（不改狀態、不噴射）；達則收證，未達則標死路」
- **身分重建**：「授權重登／重註冊以重建工作階段後，再交挑戰向單階」（斷裂時優先）

禁止當建議選項：

- 「繼續 observe／再掃一輪公開 API」（公開盤已齊時）
- 未具名的「深挖／利用整包」
- 任何 payload／逐步 exploit 寫進選項正文

## 死路

- 挑戰盤存在但指揮連續拒批挑戰向／管理面 → `DEAD:await-cmd-auditable-next`（記拒批，不自嗨達標）
- 列表為空或不可讀且無管理面線索 → 退回 `web-app-evidence-ladder`／換面，不硬開利用

## 禁

- payload／PoC／writeup 路徑／flag 解法進本卡或戰情菜譜欄
